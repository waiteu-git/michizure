**対象**: Michizure（道連れ）の部屋合言葉。合言葉はサーバーへ送らず、クライアントで PBKDF2 の入力になる。
**作成**: 2026-08-11

## 🔴 検討の経緯（当初の第一候補から変更）

**当初は案A（4,096語×4語）を第一候補としていたが、検討の結果、案D（1,024語×5語・MITのみ）へ変更した。**
理由は、§1.5 で「**案Aの実質的な最大リスクはライセンスではなく語の親しみやすさ**」と指摘していながら、
第一候補がそのリスクを最大化する側（語数を増やす側）へ向いていたため。

**✅ この文書と同日（2026-08-11）にユーザー裁定で案Dが確定した。** 詳細は下の「保留中」節と
`docs/superpowers/specs/2026-08-09-michizure-phase1-design.md` §7.6 を参照。再litigate不要。

| | 案A（4,096語×4語） | **案D（1,024語×5語）** |
|---|---|---|
| 強度 | 48.0 bit | **50.0 bit（Aより高い）** |
| ライセンス | MIT + BSD。**BSD側は要確認＝黒なら成立しない** | **MIT のみ＝確認事項が消える** |
| 語の質 | 4,096語を人手で確認。**親しみやすさの判定資材が無い**（§1.5） | **1,024語＝全語を人手で通せる**。母集団はニーモニック用にキュレート済みの BIP-39 |
| 乱数 | 2^12＝偏らない | 2^10＝偏らない |
| 代償 | — | **口に出す語が1つ増える** |

⇒ **強度も高く、ライセンスの不確実性が消え、語の質も上がる。** 代償は「4語」を「5語」に変えることだけで、
ユーザー裁定の*目的*（強度は合言葉側で作る・同行者へ伝えられる）は損なわれない。

⚠ ただし**「4語」はユーザーが決めた数字**なので、勝手には変えない。判断を仰ぐ。

## 1. 推奨する単語リスト

### 1.1 結論：そのまま採用できる既成リストは存在しない

日本語で「4,096語規模・ひらがな・口頭伝達と打鍵の両方に耐えるようキュレートされた・一般公開サービスにバンドルできるライセンス」を同時に満たす公開リストは、調査した範囲では**存在しない**。よって**既存素材を合成して自前でキュレートする**しかない。

### 1.2 ⚠ 受領した調査結果と、本作業の実測が食い違った3点（両論併記）

いずれも**実測側を採るべき**と考えるが、判断材料を添えて両論を残す。

**(a) 「BIP-39 日本語に2拍語はゼロ」**
- 受領結果: 拍数分布 3拍1093 / 4拍830 / 5拍95 / 6拍21 / 7拍2、2拍語ゼロ。
- **[実測]**: 上記5区分の合計は 2,041 で、残り7語が**2拍語**（きゃく・しゃこ・じゃま・しゅみ・ばしょ・ひしょ・ほしゅ）。
- 判断材料: BIP-39 の明文要件は「**No more words less than 3 characters**」＝**文字**基準であり、拍基準ではない **[一次]**（PR #92）。受領結果は文字数を「拍」と呼んでいた可能性が高い。**Michizure は「文字」と「拍」を最初に定義して混ぜないこと。** 本書は以下すべて**文字（NFC 後のコードポイント）基準**で書く。

**(b) 「MIT 素材は BIP-39 2,048 + Monero 1,626 ＝ 計約3,600語」**
- **[実測]**: **Monero 日本語リストは BIP-39 日本語リストの部分集合**（積集合 1,626、和集合 **2,048**）。増分はゼロ。
- 帰結（重要）: **MIT だけで使える日本語語彙は 2,048語しかない。** 4,096語に到達するには diceware-ja（BSD）が**必須**になる。ライセンス判断が語数選択に直結する（§1.4）。

**(c) 「語長は3〜5拍に寄せる」の根拠**
- BIP-39 の実測上限は **7文字（7拍）** **[実測]**。上限5は先例ではなく **Michizure 独自の設計判断**（打鍵コスト由来）。根拠として BIP-39 を引かないこと。

### 1.3 受け入れ条件（すべて CI テストとして自動化する）

人手だけでは漏れる。**世界で最も使われている日本語ニーモニックにも「きゃく / きやく」が1組残っている [実測]。**

1. 全語ひらがなのみ（U+3041–U+3096）、重複ゼロ
2. **prefix-free**（どの語も他語の接頭辞でない）
3. **先頭3文字が全語で一意**（BIP-39 と Monero が独立に同じ線へ収束 **[実測]**）
4. 語長 **3〜5文字**、かつ **3拍以上**（2拍語を排除）
5. 濁点/半濁点を剥がすと同型になる語を同居させない
6. 「X」と「X+い」「X+う」を同居させない
7. 小書き仮名（ゃゅょぁぃぅぇぉっゎ）を並書きに畳んで衝突しない
8. おう→おお / えい→ええ / ぢ→じ / づ→ず と潰した音韻キーで衝突しない
9. 「ー」を含む語ゼロ、外来語ゼロ、固有名詞ゼロ

> **[実測] 条件2と条件6は、条件3＋条件4から自動的に従う。** 最短3文字かつ先頭3文字が一意なら、ある語が他語の接頭辞になることはあり得ず（接頭辞なら先頭3文字が一致する）、X+い も自動的に排除される。**CI には独立要件として残す**（テストは壊れ方が違うため）が、リスト構築時に個別調整は不要。

条件5・6 は放置すれば必ず混入する: 辞書由来の diceware-ja には 626組・176組が実在し **[実測]**、作者自身が README の「問題点」に「『早稲(わせ)』と『和製(わせい)』が含まれてしまっている…口頭で伝達しなければならない場合には、どちらか区別することが難しいだろう」と書いている **[実測]**。

### 1.4 語数の選択肢 — **ここは要判断（§5 保留中 (1)）**

**[実測] 構成可能性を実際に検証した。** 3素材のかなを合併（ユニーク 9,016語）し、条件1〜9 を全部満たすよう貪欲構成した結果:

- **条件1〜9 をすべて満たす最大構成 = 6,534語**（内訳: BIP-39 由来 2,004 / diceware-ja 由来 4,530）
- **MIT のみ（BIP-39 単独）の上限 = 2,004語**
- 検算: prefix-free 違反0、X+い/う 共存0、先頭3文字重複0、文字長分布 3字2814 / 4字3327 / 5字393

したがって:

| 案 | 語数 | 語数の性質 | 合言葉の語数 | エントロピー | 実現可否 **[実測]** | ライセンス依存 |
|---|---|---|---|---|---|---|
| **A（推奨）** | 4,096 | 2^12 | 4語 | **48.0 bit** | 可（6,534語から選抜／余裕2,438語） | MIT + BSD |
| B（ユーザー裁定値） | 5,000 | 非2べき | 4語 | 49.15 bit | 可 | MIT + BSD |
| C | 4,096 | 2^12 | 5語 | 60.0 bit | 可（打鍵15〜25文字） | MIT + BSD |
| **D（ライセンス最小）** | 1,024 | 2^10 | 5語 | **50.0 bit** | 可（2,004語から上位半分を選抜＝語の質を最優先できる） | **MIT のみ** |
| E | 8,192 | 2^13 | 4語 | 52.0 bit | **不可**（上限6,534語 < 8,192） | — |

**立場**: 第一推奨は **A（4,096語×4語＝48.0 bit）**。ユーザー裁定の 5,000語（49.15 bit）との差 1.15 bit は PBKDF2 の反復回数を約2.2倍にすれば埋まる一方、5,000語は乱数から一様に語を引くのに棄却サンプリング（13bit 引いて 5,000以上を捨てる＝採択率 61.0% **[実測]**）が必須になる。難しくはないが、`% 5000` と書いても動いてしまい**偏りがテストに出ない**＝静かに壊れる典型箇所である。2^12 なら 12bit をそのまま切り出すだけで原理的に偏らない。

**ただし D も強く検討に値する**。D は diceware-ja に依存せず、語彙が既にキュレート済みの BIP-39 のみで完結するため、(i) ライセンス確認が MIT 1本で済む、(ii) 不快語の人手全通し確認が 1,024語で済む、(iii) **語の親しみやすさが最も高くなる**（§1.5 の最大リスクを回避できる）。代償は「4語」というユーザー裁定を「5語」に変えること。

**⚠ 受領結果にあった「より強くしたいなら 8,192語(13bit)×4語＝52bit」は、本作業の実測により実現不可能**（全条件を満たす最大構成が 6,534語）。エントロピーを増やしたい場合の道は「語数を増やす」ではなく「**語の本数を増やす（C）**」しかない。

### 1.5 語の親しみやすさ — **最大の未解決リスク**

条件1〜9 は機械的に通っても、**語が親しみやすいかは別問題**。実際に貪欲構成した結果の抽出例 **[実測]**:

- 良い例: `きんし・やりとり・こぜに・かかえる`
- 悪い例: `あとがき・たぎご・せいでんき・けつぜい`

diceware-ja は Juman の `ContentW.dic` から名詞を機械抽出したもの **[実測]** で、難易度・頻度による選別がされていない。**6,534 → 4,096 への絞り込みで効かせるべき主軸はここ**であり、余裕は 2,438語しかない。

- 最も欲しい資材である**日本語教育語彙表**（17,908語・6段階難易度・JLPT等級付き）は「研究・教育のための利用に限定します」「本語彙表の二次配布はご遠慮ください」と明記されており **[一次]** `https://jhlee.sakura.ne.jp/JEV/`、**一般公開サービスにバンドルできない**。
- 代替案（**⚠未確認**、§5-(4)）: diceware-ja の CSV は漢字表記の列を持つ **[実測]** ので、「構成漢字がすべて教育漢字（または常用漢字）」という条件で親しみやすさを近似できる。ただし機械可読な字種データの入手元とそのライセンスは未確認。
- 併せて **BIP-39 由来の 2,004語を無条件で優先採用**する（既にニーモニック用途でキュレート済み）。残り約2,092語を diceware-ja から選ぶ、という順序にする。

### 1.6 不快語・固有名詞

**既存の日本語リストを流用しても不快語対策は付いてこない＝自前の工程として必ず計上する。**

- EFF は英語リストについて "We manually checked and attempted to remove as many profane, insulting, sensitive, or emotionally-charged words as possible" と明記 **[一次]** `https://www.eff.org/deeplinks/2016/07/new-wordlists-random-passphrases`
- 一方、BIP-39 日本語リストの PR #92 には不快語スクリーニングの議論が存在しない **[一次]** `https://github.com/bitcoin/bips/pull/92`
- diceware-ja README は固有名詞除去に言及していない **[実測]**（記載は「ローマ字表記が紛らわしくなる語彙を削除する」のみ）

工程:
1. 公開フィルタ資材（inappropriate-words-ja／MIT）で機械濾過 — **⚠ライセンスと収録内容は本作業では未検証（§5-(3)）**
2. 最終語数を**人手で全通し確認**（4,096語なら現実的、1,024語ならさらに容易）
3. **人・身体・病気・宗教・国籍に関する語をカテゴリごと落とす**（語彙を数百語減らすだけで事故面積が激減する。§1.5 の余裕 2,438語の範囲で吸収可能）

**「4語の並びが失礼な句になる」問題**: EFF・BIP-39・Monero・diceware-ja のいずれについても、複数語の組み合わせに対策した一次情報は**見つけられなかった（⚠未確認）**。前例が無い＝自分で決める領域。最小実装は (a) 生成画面に必ず「**別の合言葉にする**」ボタンを置く（再抽選できる）、(b) 上記3のカテゴリ削除で母集団から消す。(b) が最も安い。

### 1.7 やってはいけない素材の使い方

- **BIP-39 の `japanese.txt` をコピペしてそのまま使う。** **[実測]** ファイル実体は NFKD で、「だ」が U+305F + U+3099 として入っている（濁点結合文字が 683箇所）。IME 出力（通常 NFC）との単純な文字列比較が静かに全滅する。**取り込み時に必ず NFC へ正規化して保存する。**
- **日本語教育語彙表をバンドルする**（§1.5）。
- **8,192語を目標にする**（§1.4、実現不可）。

## 2. 保持する表記と、入力で受ける表記

日本語で最も事故るのはここ。**「生成・保持・表示は1形に固定、入力だけ緩く受ける」**が原則。

### 2.1 保持・生成・表示（厳格側）

- 表記は**ひらがなのみ**、**NFC 合成形**の1形だけ。カタカナ・漢字・ローマ字・長音記号「ー」は**保持しない**。
- 根拠 **[一次]**: BIP-39 日本語がひらがな専用になった理由が PR #92 に明記されている — 漢字は同音異義語だらけで記憶性を下げること、"Hiragana is easier to write down by hand than Kanji and Katakana, and will be easy for all ages."
- 副次効果: かなで持てば「こうしょう」問題は消え、**リスト内で読みが重複しないことだけ保証すればよい**。「はし（箸／橋）」のような高低アクセントだけの差も文字列としては同一になり、聞き手がアクセントを取り違えても鍵は一致する。
- **表示の区切りは中黒「・」**。BIP-39 は表意空白 U+3000 を採り、正規化で ASCII 空白に潰している **[一次]** `https://github.com/bitcoin/bips/blob/master/bip-0039/bip-0039-wordlists.md`＝「表示に使う区切り」と「鍵導出に入る区切り」を分離する設計には前例がある。

### 2.2 入力受理パイプライン（順序を固定する。順序が仕様の一部）

```
①NFKC → ②カタカナ→ひらがな畳み込み（U+30A1–U+30F6 を −0x60）
→ ③区切り・空白類を全除去（半角/全角空白・中黒・半角中黒・読点・ハイフン・「ー」・アンダースコア・改行）
→ ④NFC → ⑤語境界の復元と検証 → ⑥PBKDF2

🔴 **2026-09-05: 実装に ④ が無く、それが実際の欠陥だった（kdfVersion 2 で修正）。**

この場所には同日の早い時刻に「④は no-op。3,118 件の実測で結果を変えるケースは0件」と
書いていた。**その主張は誤りで、同じ監査が数時間後に反証した。**

- 反例＝`みすﾞうみ・こは゛ん・つは゛め・ひので`（下の受理表の6件目そのもの）。
  `normalizePassphrase` は `…こ` + `は`+U+3099 + `ん…` を返し、合成形の `こばん` と**別の文字列**になる。
```

## 3. 提示と共有の導線

前提: **合言葉を紛失すると復旧不能**（サーバーに鍵が無い）。したがって導線は「強度」ではなく「**確実に相手へ届き、かつ作成者の手元から消えないこと**」を最優先で設計する。

### 3.1 口頭を主動線にしない

かな1文字の口頭伝達は、**公的に「そのままでは通らない」と扱われている水準の問題**である。無線局運用規則 第14条・別表第5号が和文通話表を定め、固有の名称・数字・つづりの複雑な語辞等を一字ずつ送信する場合の使用を義務づけている **[二次]**（§5-(5)）。

したがって:

- **主**: QR コード／ワンタップコピー／OS の共有シート（LINE 等へ貼る）
- **副**: 口頭。取りこぼしは「**先頭3文字サジェスト**」で救う（条件3のおかげで先頭3文字だけで語が一意に決まる **[実測]**）。1文字聞き逃しても復旧できる。

### 3.2 生成画面の要件

1. 中黒区切りで大きく表示（例: `みずうみ・こばん・つばめ・ひので`）
2. **「別の合言葉にする」ボタンを必ず置く**（§1.6 の組み合わせ事故への最小対策を兼ねる）
3. **「この合言葉は復元できません」を、コピーより前に、閉じられない位置で明示する**
4. コピー／QR／共有シートの3ボタン
5. 「控えた」の明示的チェックを通すまで部屋作成を完了させない
6. 端末ローカル保存は任意（保存しない選択を必ず残す）

### 3.3 URL / QR に載せるか — **要判断（§5 保留中 (2)）**

**[実測] 長さ（例の合言葉で計測）:**

| 形式 | 文字数 | UTF-8 バイト | パーセントエンコード | base64url |
|---|---|---|---|---|
| 中黒付き `みずうみ・こばん・つばめ・ひので` | 16 | 48 | 144 文字 | 64 文字 |
| 区切り除去 `みずうみこばんつばめひので` | 13 | 39 | **117 文字** | **52 文字** |

素のパーセントエンコードでは QR が無用に大きくなる。載せるなら**区切り除去後の正規形を base64url**（52文字）。

**ただし「載せるか」自体が別の判断**: 載せた瞬間に「**URL を渡せる相手＝部屋に入れる相手**」になる。URL はチャットの履歴・プレビュー生成・ブックマーク・スクリーンショットに残る。載せる場合はフラグメント（`#`）に置く前提だが、フラグメントがサーバーへ送られないことの一次確認は未了（§5-(6)）。

## 4. 「自分で決める」場合の最低要件

**設計判断（一次情報の裏付けは無い）。** 目標は既定生成（48〜50 bit）と極端に乖離させないこと。

### 4.1 方式の第一推奨: 「自由入力」ではなく「語の差し替え」

最も安全なのは、自分で決めたい人にも**リストの語から選ばせる**こと（4つの語をそれぞれ引き直す／候補から選ぶ UI）。この方式なら**強度が定義上そのまま数えられ**、正規化・prefix-free・エラー表示の資産がすべてそのまま効く。まずこれを提示し、完全自由入力は「それでも自分の言葉にしたい人」向けの二次導線にする。

### 4.2 完全自由入力を許す場合の最低要件（すべてクライアント判定）

進めさせない条件（1つでも該当したら不可）:

1. 正規化後（§2.2 のパイプライン適用後）の**文字数が16未満**
2. **異なり文字数が8未満**（`ああああああああああああああああ` を弾く）
3. 同一文字の**3連続**を含む
4. 五十音順の連続・キーボード配列の連続・8桁の日付らしい数字列など、**既知の弱いパターン**に一致する
5. 既定生成リストの語のみで構成されている場合に、**語数が4未満**

### 4.3 併せて必須の設計

- **判定は必ずクライアントで完結させる。** 合言葉をサーバーへ送らない設計が本サービスの根幹であり、外部の漏洩パスワード照会（k-anonymity 方式を含む）も**使わない**。判定のために合言葉を端末外へ出した時点で設計が壊れる。
- 強度メーターを出す場合の実装候補（zxcvbn 等）は、**日本語辞書を持たないライブラリが日本語文字列を過大評価する**危険がある。採用するならライセンスと日本語での挙動を検証してから（§5-(7)）。
- 「自分で決める」を選んでも、**復旧不能の警告と控えの確認は既定生成と同一**にする。
