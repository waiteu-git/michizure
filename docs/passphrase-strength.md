# 合言葉の強度と PBKDF2 反復回数 — 分析と方針案

作成日: 2026-08-10
背景: 法務下調べ（ビジネスハブ）により、**「サーバーが `SHA-256(authKey)`＋salt を持つ構成では、同時漏えい時に弱い合言葉へのオフライン辞書攻撃が成立しうる」**ことが論点になった。設計 §16 の「PBKDF2 反復回数」を**端末性能だけで決めてはいけない**。

> ⚠ **法的評価はここでは行わない。** 「この構成なら例外に当たる」とは書かない。照会の回答待ち。
> ここで出すのは、判断に必要な**技術的な事実と選択肢**だけである。

## 前提と、どこまでが実測か

| | 値 | 種別 |
|---|---|---|
| PBKDF2 600,000回（Mac M1 / **Node** の WebCrypto） | **73ms** | ✅ 実測（`scripts/bench-pbkdf2.mjs`） |
| PBKDF2 600,000回（Mac M1 / **ブラウザ**の WebCrypto） | **173ms** | ✅ 実測（`bench/pbkdf2.html` を localhost で実行） |
| 利用者端末（Android/iPhone）での所要時間 | 未測定 | ⏳ `bench/pbkdf2.html` で測る |

⚠ **同じ機械でもブラウザは Node の約2.4倍遅い。** 実際に走るのはブラウザなので、
Node の値で「速いから大丈夫」と判断すると2倍以上外す。**ローエンド端末ではさらに開く**。
| 攻撃者の GPU が CPU1コアの何倍か | **1,000〜3,000倍と仮定** | ⚠ **仮定**（測定していない。PBKDF2-HMAC-SHA256 の一般的な並列化効率からの見積もり） |

以下の年数は**この仮定の上での計算結果**であって、測定値ではない。桁の感覚をつかむために使う。

## 結論: 効くのは合言葉であって反復回数ではない

反復 600,000 回・攻撃者が 1,000〜3,000倍のとき、平均的な総当たり時間:

| 合言葉の作り方 | 強度 | 割られるまで |
|---|---|---|
| 4桁の数字 | 13 bit | **0.1〜0.4秒** |
| よくある単語1つ（例:「あいことば」「おきなわ」） | 17 bit | **1〜4秒** |
| ランダムな単語2つ | 25 bit | 5〜15分 |
| ランダムな単語3つ | 37 bit | 18〜53日 |
| **ランダムな単語4つ** | **49 bit** | **241〜723年** |
| ランダム英数字8文字 | 48 bit | 84〜253年 |

**反復回数を2倍にして得られるのは 1 bit。5,000語から単語を1つ足すと 12.3 bit。**
⇒ 反復回数を600,000から1,200,000へ倍にしても「よくある単語1つ」は 1〜4秒が 2〜7秒になるだけで、**守れない状態は変わらない**。

⚠ 現在テストやE2Eで使っている「たびのあいことば」「おきなわのあいことば」のような合言葉は、**この表でいう最下段に属する**。

## 方針案（ユーザーの選択）

反復回数は「一番遅い端末が耐えられる上限」で決め、**強度は合言葉側で作る**。その作り方の選択:

### 案1: 生成した合言葉を既定にする（推奨）

部屋を作るとき、**日本語の単語4つをランダムに組み合わせた合言葉を既定で提示**する（例:「みずうみ・こばん・つばめ・ひので」）。利用者は「自分で決める」を選べるが、その場合は最低要件を満たすまで進めない。

- 利点: **旅行の同行者へ口頭で伝えられる**（QRやURLと一緒に共有する場面に合う）。強度が利用者の語彙センスに依存しない
- 利点: 「合言葉を紛失すると復旧できない」という制約とも相性がよい（提示時にコピー/保存を促せる）
- 欠点: 「好きな言葉にしたい」利用者には一手間。単語リスト（5,000語程度）をアプリに同梱する必要がある（数十KB）

### 案2: 自由入力のみ＋強度メーター

入力欄の下に強度を表示し、弱ければ警告する。止めはしない。

- 欠点: **警告は読まれない。** 実効は案3とほぼ同じになりやすい

### 案3: 現状のまま（制限なし）

- 欠点: 上表の最下段が既定になる。**設計 §7.4 の「想定する脅威は合言葉を知る友人」という前提が、漏えい時の議論では通らない**

## 反復回数そのもの

実機測定（`bench/pbkdf2.html`）の結果で決める。目安:

- 入室のたびに1回だけ走る ⇒ **1秒までは許容、2秒超なら下げる**
- **一番遅い端末に合わせる**（速い端末の値で上げない）
- 上げても得られるのは1回の倍加あたり1 bit ⇒ **体感を削ってまで上げる価値は薄い**。案1と組み合わせるなら 600,000 のままで十分に釣り合う
