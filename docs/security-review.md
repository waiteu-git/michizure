# セキュリティレビューの記録

開発中に社内レビューで見つかった問題と、その対応状況をまとめたもの。
正直に書くことを優先し、直したものも直していないものも両方載せる。

## 直したもの

- **総当たり対策の迂回**: 削除エンドポイント（`DELETE /api/rooms/:id`）が、入室エンドポイントと
  別の認証チェックを持っていたため、入室側のバックオフを迂回できた。共通の認証関数に集約した。
- **形式検査の抜け**: WebSocket 経由の更新（`update` メッセージ）が、REST 経由の更新（`PUT`）と
  同じ形式検査を通っていなかった。3経路すべてで同じ検査を通すよう統一した。
- **`/ws` の Upgrade ヘッダ未検証**: WebSocket のハンドシェイクで `Upgrade: websocket` を確認せずに
  接続を受け付けていた。確認するよう修正した。
- **入室トークンの接続後の失効**: WebSocket 接続を張った後は、トークンの期限が切れても接続が
  生き続け、更新の送受信ができてしまっていた。書き込みを受ける時・他の端末へ中継する時の両方で
  期限を確認し、切れていれば通知して接続を閉じるようにした。
- **鍵導出パラメータの未保存**: PBKDF2 の反復回数を部屋ごとに保存していなかった。既定値を将来
  変更した時に、既存の部屋が復号できなくなる欠陥だったため、部屋ごとに保存するよう修正した。
- **入室失敗回数の未減衰**: 入室失敗の回数が時間とともに減らず、一度の連続失敗が恒久的にブロックへ
  つながりうる形だった。24時間で減衰するよう修正した。
- **存在しない部屋への読み取りでストレージが作られる**: 存在しない部屋 ID への読み取りアクセスだけで、
  空のストレージが作成され、残り続ける問題があった。ストレージの作成を書き込み時のみに限定した。

## まだ直していないもの（承知のうえ）

- **部屋の作成の速度制限は「全体で1つ」のバケットで、1人が使い切れる**: このアプリは IP アドレスを読まない
  設計のため、相手ごとには制限できない。`handleCreateRoom` は Durable Object（`CreateLimiter`）の
  トークンバケット（容量20・1分で20個戻る）から1つ取る。Durable Object は1度に1つのリクエストしか
  処理しないので、同時に何本来ても上限を超えない（強整合）。
  最初の版は Cloudflare の Workers Rate Limiting binding を使ったが、**本番で実測すると約195回連続で
  作成しても一度も 429 が返らなかった**（2026-09-18）。原因は不具合ではなく、公式ドキュメントがこの機能を
  「permissive・eventually consistent・正確な計数には使わない設計」と明記していること。
  **正確さが要る歯止めに、正確さを保証しない道具を使った**のが問題の本体だったので、Durable Object の
  カウンタへ置き換えた。
  残る性質: 相手を区別しない全体の上限なので、1人で使い切ると他の人も1分間は作れない（入室・同期・既存の
  部屋の削除は影響しない）。カウンタが答えられない時は、素通しにせず 503 で作成を断る。カウンタが保存するのは
  残りの回数と更新時刻の2つだけで、呼び出した相手に関するものは持たない。
  ⚠ **上限は速さを縛るだけで、総量は縛らない**: 1日最大 28,800 部屋・1部屋最大 256 KiB・365日で自動削除なので、
  続けて悪用されれば無料枠は数日で埋まりうる。
  なお、溜まるのは暗号文の入った空の部屋であって、誰かの情報が露出する形ではない。
  実害は無料枠の消費と保存領域の使用に限られる。
- **削除後の内部スケジュール処理（alarm）の残留を確認するテストが無い**: 部屋を削除すると、
  暗号文・認証情報・KV に書いた値はすべて消えることをテストで確認している。ただし、部屋には
  「1年間アクセスが無ければ自動削除する」ための内部的なスケジュール処理（Durable Object の
  alarm）が仕掛けられており、手動削除時にこれが確実に解除されているかを直接確認するテストは、
  今のところ無い。解除する処理自体は呼んでいるが、**呼んだことの検証が無い**という状態。
  実害は無い可能性が高い（削除済みの部屋に対して後から自動削除が走っても、対象データは
  既に無い）が、テストで裏を取れていない以上、直したとは書かない。

## 方針として意図的にやっていないこと

- **IP アドレスを読まない**: 上記のレート制限を「相手ごと」でなく「全体で1つ」にしているのは、
  この設計判断の帰結（相手を区別する手段を持たない）。詳しくは README の
  「What the server actually holds」を参照。
- **削除済みの部屋と、最初から存在しない部屋を区別しない**: 区別するには「削除済みの目印」を
  残す仕組みが要り、「削除＝完全に消える」という設計上の約束に例外を作ることになる。
