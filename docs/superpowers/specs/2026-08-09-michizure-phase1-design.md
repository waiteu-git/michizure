## 3. スコープ

### Phase 1（本設計の対象）

部屋モデル、合言葉による鍵導出と認証、クライアントサイド暗号化、Cloudflare への移設、フロントの部屋対応、インポート導線、オフライン対応、プライバシーポリシーと削除導線。

### Phase 2（別 spec）

PWA 化。Phase 1 を実利用してから設計する。

⚠ **Service Worker だけは 2026-09-05 に Phase 1 側へ入った**（§9）。オフラインでの再読み込みが
Phase 1 の「オフライン対応」に含まれる以上、Phase 2 まで待てなかったため。**manifest とインストール導線は
まだ無く、Phase 2 のまま**＝「SW があるから PWA 化は済んだ」と読まないこと。

### Phase 3（別 spec・実施は要再判断）

Capacitor でラップしてストア提出。§4 の調査結果により、**実施するかどうか自体を Phase 2 の実利用結果を見てから判断する**。

### 非スコープ

- 外貨対応（Walica が150通貨対応済み）
- レシート読み取り（レコペイが実装済み）
- 完全な自動マージ（CRDT）。オフライン衝突は検出してユーザーに提示する方式に留める
- **合言葉の変更**（全データの再暗号化が必要になるため。Phase 2 以降で検討）
- **合言葉を紛失した場合の復旧**（構造上不可能。§7.5 参照）
- 現行版の改造・停止・データ移動

## 4. 差別化の軸と根拠

2026-08-09 に競合調査を実施。**当初想定していた差別化候補は、いずれも既存サービスが実装済みだった。**

| 当初の候補 | 調査結果 |
|---|---|
| 精算済みチェックの追跡 | 既存にあり |
| 対象者ごとの割り勘 | 既存にあり。さらにメンバーごとの減額設定まである |
| リアルタイム同期 | 既存にあり |

競合: Walica（累計500万ユーザー・個人開発）、タテカリ、レコペイ、groupay、Nowa、Walimo、FAMI-KAN、ワリナビ、TATEKA、Splitwise ほか。**機能面での優位は見つからなかった。**

### 4.1 旅行特化

現行アプリは既に旅行の語彙で書かれており、後付けではない。支出を `booking`（予約）と呼び、カテゴリが航空券 / 宿泊 / 食費 / 交通費 / アクティビティで、出発前の立替と現地費用が自然に混在する。

設計上は**部屋 = 1つの旅行**とし、名前と期間を第一級の属性として持たせる。

### 4.2 オフライン耐性

Walica もタテカリもブラウザのグループページであり、電波がないと使えないと推測される。旅行で記録したい場面は山中・海外・機内・地下に偏る。

**注記: 競合のオフライン挙動は未検証である。** この軸の優位性は仮説であり、§16 に検証項目として記載する。

### 4.3 暗号化は差別化の軸に含めない

**§7.5 の限界により、「運営者にも中身が見えない」は利用者の側から検証できない。対外的な訴求に使ってはならない。** 内部の設計方針としてのみ採用する。

## 5. アーキテクチャ

```
ブラウザ ──HTTP──> Worker ──> 静的アセット（HTML/CSS/JS）
        └─WS────> Worker ──> Durable Object（部屋ID）── SQLite ストレージ
                                    ↑
                          暗号文のまま保存・中継する
                          （復号鍵はサーバーに存在しない）
```

- Worker: ルーティングと静的配信
- Durable Object: 1部屋につき1インスタンス。**暗号文**と WebSocket 接続を保持
- ストレージ: DO の SQLite バックエンド（Workers 無料プランの対象）

部屋間の分離は DO の境界により構造的に保証される。加えて、**部屋ごとに異なる鍵で暗号化されるため、DO の境界が破れても他の部屋の内容は読めない**。

### コスト

Workers 無料枠 10万リクエスト/日、DO 無料枠 10万リクエスト/日・5GB。超過時は Workers Paid $5/月。CPU 時間の上限を wrangler で設定し、denial-of-wallet を防ぐ。

## 6. データモデル

### サーバー（DO）が保持するもの

```
meta:  { roomId, createdAt, lastAccessAt, schemaVersion }   ← 平文（メタデータ）
auth:  { salt, authKeyHash, iterations, kdfVersion }         ← salt/iterations/kdfVersion は認証前に取得可能
blob:  { ciphertext, iv, blobVersion }                       ← サーバーは復号できない
```

⚠ **`iterations` と `kdfVersion` を部屋ごとに残すこと。** 既定値や正規化の規則を後から変えると、
残していない部屋は**入室も復号もできなくなる**。`GET /api/rooms/:id/salt` が salt と一緒に返す（§7.6.1）。

### 暗号文の中身（クライアントだけが見る）

```
RoomState {
  name: string
  startDate: string | null     // YYYY-MM-DD
  endDate: string | null
  members: Member[]            // 最大20（クライアント側で強制）
  bookings: Booking[]
}

Member  = { id, name }
Booking = { id, category, description, payer, amount, participants[], paid{} }
```

**旅行名も暗号文の中に入る。** そのため入室前に部屋名を表示することはできない。URL と合言葉で入室して初めて名前が見える。

### 現行からの変更点

| 項目 | 現行 | Phase 1 | 理由 |
|---|---|---|---|
| メンバー数 | 6人固定 | 可変（最大20） | 公開する以上必須 |
| メンバー識別 | 名前の文字列 | `id` で識別し `name` は表示用 | 改名時に `payer` / `participants` / `paid` を書き換える処理が不要になる |
| booking の id | クライアントが `nextId` を採番 | **クライアント生成の UUID** | オフラインで採番すると連番は必ず衝突する |
| 旅行期間 | なし | `startDate` / `endDate` | 旅行特化の軸 |
| サーバーから見た状態 | 平文の JSON | **暗号文** | §7 |

`category` / `description` / `payer` / `amount` / `participants` / `paid` の意味と構造は現行と同一に保つ。インポートが素直に通り、検証済みロジック（`parts()` / `isDone()` / `settle()`）をほぼそのまま移植できる。

## 7. 鍵導出・認証・暗号化

### 7.1 鍵導出

すべてクライアント側で行う。**合言葉そのものはサーバーへ送信しない。**

```
master  = PBKDF2(passphrase, salt, iterations, SHA-256) → 32 bytes
authKey = HKDF(master, info = "michizure-auth-v1")      → 32 bytes  ← サーバーへ送る
encKey  = HKDF(master, info = "michizure-enc-v1")       → AES-GCM 256bit ← 送らない
```

- `salt` は部屋ごとにランダム生成（16 bytes）。秘密ではないため `GET /api/rooms/:id/salt` で認証前に取得できる
- `iterations` は実装時に対象端末（ローエンドのスマートフォンを含む）で実測して決める。**§16 の未決事項とする**
- `authKey` と `encKey` は別の `info` から導出されるため、`authKey` が漏れても `encKey` は導出できない

### 7.2 認証

サーバーは `SHA-256(authKey)` と `salt` のみを保存する。

| | サーバーが持つ | 持たない |
|---|---|---|
| 合言葉の平文 | | ✓ 持たない |
| `encKey`（復号鍵） | | ✓ 持たない |
| `authKey` | 受信するが保存しない | |
| `SHA-256(authKey)` | ✓ 保存する | |
| `salt` | ✓ 保存する | |

現行設計（合言葉を POST してサーバーで検証）と比べ、**サーバーが合言葉の平文を一度も受け取らない**点が改善している。

総当たり対策は DO 内で失敗回数を数え、指数バックオフする。部屋ごとに DO が1つなので、分散カウンタなしで正しく数えられる。

### 7.3 暗号化

- AES-GCM 256bit。**暗号化のたびに 96bit の IV をランダム生成する**（再利用は GCM で致命的）
- 平文は `RoomState` の JSON
- `blobVersion` を持たせ、将来の方式変更に備える

### 7.4 サーバー側検証ができなくなること

サーバーは中身を読めないため、現行設計にあった `validateState`（メンバー20人上限、payer の存在確認、participants の妥当性）は**サーバー側では実行できない**。

- **20人上限はクライアント側でのみ強制する。これは強制ではなく約束にすぎない。** 改造したクライアントは超過できる
- サーバー側の防御は**暗号文のバイト数上限**（256KiB）と、**暗号文の「形」の検査**（`ciphertext` / `iv` が文字列であること・`iv` の長さが妥当であること）のみ。これは濫用とストレージ枯渇を防ぐためのもので、データの正しさは保証しない
  - ⚠ **単位に注意**（2026-08-10 に実装が取り違えていた）。`ciphertext` は base64 の**文字列**なので、その文字数を 256KiB と比べると実際の上限が 3/4（192KiB）に縮む。比較は必ず復号後のバイト数で行う。base64 に載せた状態では約 341KiB になる
  - ⚠ `ciphertext` だけを見ると `iv` など他のフィールドが素通りする。**上限は「1つのフィールド」ではなく「保存するもの全体」に効かせる**（生の本文長の足切りを作成・更新・WebSocket の全経路に置く）
- 想定する脅威は「合言葉を知る友人」であって攻撃者ではない。この前提が崩れる用途には向かない
  - 🔴 **この一行だけを読んで脅威モデルを組まないこと**（2026-09-05 追記）。実装では復号鍵と平文の控えが
    端末の `localStorage` に残るので、**想定脅威には「その端末を触れる人」が実際には含まれている**。
    §9 の🔴節が正典
- ⚠ **「IPを読まない」ことの代償**（2026-08-10に判明）。クライアントを区別する手段が無いので、
  **クライアント単位のレート制限ができない**。結果として次の2つは塞げていない:
  - 部屋の作成が無制限（Cloudflare 側のレート制限で対処する）
  - URLを知っている人なら誰でも、合言葉を外し続けてその部屋を締め出せる
  ⇒ **privacy の選択が防御の選択肢を狭めている**という関係を、後から「なぜ塞がないのか」と
  問われた時に思い出せるよう記録しておく

### 7.5 🔴 この暗号化の限界（設計者が忘れてはならない）

**利用者はこの暗号化を検証できない。**

**Web アプリでは、クライアントの JavaScript を配信しているのが運営者自身である。** 運営者が配信コードを差し替えれば、合言葉も平文も取得できる。したがって「暗号化しているから運営者には見えない」は厳密には成立しない。E2E を名乗る Web サービスに共通する構造的限界であり、Michizure も例外ではない。

⇒ **内部の設計方針としては採る。対外的な訴求には使わない。** 「運営者にも中身が見えない」等の文言を、サイト・ストア説明文・プライバシーポリシーに書いてはならない。**証明できない安全性を売り文句にすると、一度でも崩れたときに信用がまとめて失われる。**（署名付きで配布されるネイティブアプリでは前提が変わるが、それは Phase 3 以降の話）

**メタデータは暗号化されない。** 以下はサーバーに残る。

- 部屋の存在と部屋ID
- 作成時刻・最終アクセス時刻
- **IPアドレス**（Cloudflare のログ）
- 暗号文のサイズ（参加人数や予約件数がおおよそ推測できる）
- 更新の頻度とタイミング

⇒ **「何も持たない」ではない。「暗号文とメタデータを持つ」である。** 法務照会もこの前提で立てる（§16）。

**合言葉を紛失すると復旧できない。** サーバーに鍵がないため、運営者にも復旧手段がない。**UI で明示的に警告する**こと。

### 7.6 合言葉の強度（2026-08-11 裁定・再litigate不要）

**反復回数をいくら上げても弱い合言葉は守れない。** 反復を2倍にして得られるのは 1 bit、
5,000語から単語を1つ足すと 12.3 bit。⇒ **強度は合言葉側でしか作れない。**

**🔴 2026-08-11 裁定＝1,024語のリストから5語（約50bit）。再litigate不要。**

- **部屋を作るとき、ランダムな5語の合言葉を既定で提示する**
- 「自分で決める」も選べるが、最低要件を満たすまで進めない（二段構えは維持）
- 紛失＝復旧不能なので、**提示の瞬間が保存を促す唯一の機会**

なぜ 1,024語×5語か（4,096語×4語ではなく）:

| | 4,096語×4語 | **1,024語×5語（採用）** |
|---|---|---|
| 強度 | 48 bit | **50 bit** |
| ライセンス | MIT + BSD。**BSD側は他プロジェクトへの参照で未確認** | **MIT のみ＝確認事項が消える** |
| 語の質 | 4,096語を人手で確認。**親しみやすさの判定資材が無い** | **1,024語＝全語を人手で通せる**。母集団は BIP-39 のキュレート済み日本語 |
| 代償 | — | 口に出す語が1つ増える |

**語数を増やしても意味が無い。** 1語=10bit なので 4語=40bit は**155日〜1年で割れる**（＝1,024語なら5語が下限）。
一方 5語=50bit は 434〜1,303年、6語=60bit は44万年〜。**5語で既に脅威の外側**であり、
上限を決めているのは強度ではなく**人が正しく運べるか**（写し間違い／面倒で「自分で決める」へ逃げて弱くする）。
5語に固定しておくと**リストが人手確認で縮んでも耐える**（512語まで減っても45bit）。

⚠ **最低要件は「語数」で測ってはいけない**（「あいうえお」×5 が通ってしまう）。**推定エントロピーで測る。**

🔴 **合言葉は鍵に通す前に必ず Unicode 正規化する。** 日本語の濁点は2通りの
表し方があり（「みずうみ」= 合成済み / 基底+結合濁点）、正規化しないと**端末や入力方法の差で
鍵が変わり「正しい合言葉なのに入室できない」**が起きる。症状から原因が全く見えない種類の不具合。

⚠ **正規化形は §7.6.1 ③ が正典＝NFKC**（実装も `keys.ts` の `normalizePassphrase` で NFKC）。
この段落は当初 NFC と書いており、**§7.6.1 の裁定（2026-08-11）以降ずっと同一文書内で矛盾していた**
（2026-09-05 に BH の監査が指摘して修正）。⚠ **層で形式が違う**＝合言葉は NFKC、
**単語リストのファイル実体は NFC**（BIP-39 の原本が NFKD なので取り込み時に変換）。混ぜないこと。

### 7.6.1 合言葉の受け渡しと入力（2026-08-11 裁定・再litigate不要）

**① 自分で決める場合の最低要件は、語数ではなく推定エントロピーで測る。**
「5語以上」のような語数の条件は「あいうえお」×5 が通ってしまう。

**② 合言葉を URL・QR に載せない。**

> 🔴 **2026-09-06 追記: 「暗号文を QR に載せる」はこの規則に反しない。**
>
> 圏外入室券（§9.1）は `#t=` に **salt・反復回数・kdfVersion・iv・暗号文** を載せる。
> これらは**合言葉ではない**し、合言葉を導けもしない。券を拾った人にできるのは
> 総当たりだけで、それは部屋 ID を知った人が最初からできることと同じである
> （生成合言葉は約50bit・PBKDF2 600,000回）。
>
> ⚠ **区別が要るのはここ**: ②が禁じているのは「**リンク1本で部屋が開く**状態」を
> 作ること。券は開かない——受け取った人は必ず5語を別経路で聞く必要がある。
> つまり券は②を破るどころか、**②が要求する「別々に渡す」を圏外へ広げる**ものである。
>
> ⚠ ただし**カスタム合言葉の部屋では券を発行しない**。弱い合言葉の暗号文が
> 手元に渡ると、通信も待たずに**無制限のオフライン総当たり**ができる。
> サーバー側のバックオフ（§7.4）は、暗号文が手元に無いことを前提にしている。
載せればリンク1本で済むが、**リンクが漏れた時点で部屋も漏れる**（スクリーンショット・
転送されたチャット・共用端末の履歴）。⇒ **既定は「リンクと合言葉を別に渡す」**。
理由は非対称性＝**まとめて送ると取り消せないが、分けて送ったものは後からまとめられる**。
取り返しのつかない側を既定にしない。「リンクと合言葉をまとめてコピー」は選択肢として置く。

**③ 表示は中黒区切り。入力は次の順で正規化してから鍵に通す（順序も契約の一部）:**

1. **NFKC** … 濁点の合成/分解・全角半角・**半角カタカナ**を揃える
2. **カタカナ→ひらがな** … IME の状態でカタカナ確定する事故を吸収する
3. **区切りと空白を除去** … 中黒・空白・読点・ハイフン等。⚠ **`ー`（長音）と `。` は落とさない**
   （`コーヒー` → `こひ` になってしまう＝長音は単語の一部）
4. 🔴 **NFC** … **3 の後でなければならない。** NFKC は単体の濁点 `゛`(U+309B) を
   「空白 + 結合濁点」に展開するので、3 が空白を消すまで合成できない。
   ⚠ **この手順はこの節に長く欠けており、実装も持っていなかった**（2026-09-05 に監査が発見）。
   `docs/passphrase-wordlist.md` §2.2 は最初から4手順で書いており、**2つの文書が食い違ったまま
   実装がこちら（3手順）に従った**のが原因。⇒ `kdfVersion` 2 で修正済み・1 は欠陥ごと保存。

英字の大小は畳まない（カスタム合言葉では素直に情報になる）。

⚠ **NFKC は規格からの意図的な逸脱。** PRECIS（RFC 8265）はエントロピー保持のため NFC を
規定している。それでも NFKC を選ぶのは、日本語IMEでは全角英数や半角カタカナが意図せず
混入するほうが、全角半角を使い分けて強度を作る利用者より圧倒的に多いため
（`ｱ` は NFC では畳まれず、手順2のカタカナ範囲にも入らないので必ず弾かれる）。

🔴 **④ `kdfVersion` を部屋ごとに保存する。**
鍵は「合言葉 → **正規化** → PBKDF2(salt, 反復回数) → HKDF(**info**)」で決まる。
salt と反復回数は保存していたが、**正規化と info は保存していなかった**＝変えた瞬間に
既存の部屋が全部開けなくなる。**反復回数で一度学んだのと同じ形を、効くべき面で数え損ねていた。**
⇒ 保存することで、上の③（規格からの逸脱を含む）が**後から取り消せる判断**になる。

⚠ **「最低要件を強制する」と書くときは「公式クライアント上で強制」の意味に限る。**
サーバーは合言葉を受け取らないので**弱さを判定できない**＝§7.4 の「クライアント側の上限は約束にすぎない」と
同じ構造である。改造したクライアントなら弱い合言葉を使えるが、**害が及ぶのはその人自身の部屋だけ**＝
想定脅威（合言葉を知る友人）の内側に収まる。**この整理ごと書く**（「強制」だけ書くと嘘になる）。

単語リストの調査は `docs/passphrase-wordlist.md`。**ライセンスが未確認のリストは採用しない。**

**語数は確定（1,024語×5語）。** 調査で分かった要点:

- **そのまま使える日本語リストは存在しない**＝既存素材からキュレートするしかない
- **MIT だけで使える語彙は 2,048語しかない**（Monero の日本語リストは BIP-39 の部分集合で、増分ゼロ）。
  それ以上は diceware-ja（BSD）が必要だが、**そのライセンスは他プロジェクトへの参照であって明示ではない＝要確認**
- 5,000語のような**2のべき乗でない語数は乱数の切り出しに棄却サンプリングが要る**。
  `% 5000` と書いても動いてしまい、**偏りがテストに出ない**＝静かに壊れる典型
- **語の親しみやすさを機械判定する資材が無い**（日本語教育語彙表はバンドル不可）⇒
  語数が多いほど「読めない語が混ざる」リスクが上がる

⚠ **合言葉の口頭伝達を主動線にしない**（同上の調査）。表示・共有の導線は Phase 1b で設計する。

## 8. 同期

**WebSocket Hibernation API を使う**（`ctx.acceptWebSocket()`）。精算アプリは開いたまま放置される時間が長く、これを使わないとアイドル時に duration 課金が積み上がる。

サーバーは**暗号文をそのまま中継する**。中身を読まないため、検証もマージもしない。

### 送信者除外

送信元クライアントへのエコーバックは DO 側で明示的に除外する。**除外が実際に効いていることをテストで観測する。**

前身プロジェクトで、クライアント側の `suppressNext` フラグが「自分のエコーを無視する」つもりで実際には「次に届いた他端末の更新」を握り潰していた不具合があった。サーバーが送信者を除外していたためフラグは不要であり、かつ有害だった。壊れ方が「保存のたびに1回分だけ落ちる」ため、使っていて気づけなかった。**除外は片側（サーバー）だけで行い、その結果を必ずテストで確認する。**

### 衝突検出

サーバーが中身を読めないため、衝突検出は**完全にクライアント側で行う**。現行アプリで実装済みの方式（編集開始時にスナップショットを取り、更新時に比較して差異があれば確認ダイアログ）をそのまま移植する。

## 9. オフライン（ローカルファースト）

### 保証する範囲

| 操作 | オフライン時 |
|---|---|
| 閲覧 | **可能**（端末に持っている控えから描画。⚠ その控えは平文＝下の🔴節） |
| 予約の追加 | **可能**（ローカルに反映し、送信キューに積む） |
| 予約の編集・削除 | **可能**（復帰時に衝突しうる） |
| 精算チェック | **可能**（冪等操作） |
| 新規の部屋作成 | 不可（サーバーとの通信が必要） |
| 新規の入室 | **可能**（圏外入室券。§9.1） |

UI は常にローカルの状態から描画する。

⚠ **この表は「アプリ本体が読み込めていること」を前提にしている。** 記録は `localStorage` に残っても、
**圏外のままブラウザを閉じて開き直すとアプリ自体が読み込めない**＝一番ありそうな操作で詰む。
この穴は 2026-09-05 の監査まで気づかれず、同日 `public/sw.js`（`scripts/build-sw.mjs` が
ビルド成果物から生成し、`src/client/app.ts` が登録する）を足して塞いだ。
それ以前はオフラインでの再読み込みはブラウザの HTTP キャッシュ頼み＝**保証されていなかった**。
🔴 **`/api/*` はキャッシュしない**（古い暗号文や失効したトークンを返すと同期の判断そのものが壊れる）、
画面遷移は通信優先でキャッシュは落ちた時だけ、という切り分けも一緒に守ること。

### 🔴 ローカルは暗号化していない・復号鍵は端末に残る（2026-09-05 の監査で発見）

**この節は長い間「ローカルに保存する状態も暗号化する（`encKey` は合言葉から都度導出し、永続化しない。
セッション中はメモリに保持する）」と書いていたが、出荷しているクライアントはどちらも満たしていない。**

- `src/client/store.ts` … `RoomState` を `JSON.stringify` のまま `localStorage` へ書く（**平文**）
- `src/client/session-store.ts` … `{ roomId, token, encKey, name }` を `localStorage` へ持つ。
  `encKey` は base64 にした**復号鍵そのもの**で、`remembered()` がそれを読み戻す

⇒ **一度その部屋を開いた端末では、合言葉を知らない人でも中身が読め、部屋も開き直せる。**
共用端末・盗難端末・貸した端末では、部屋の合言葉は防御になっていない。§7.4 の想定脅威
（合言葉を知る友人）に「その端末を触れる人」が加わる、と読むこと。

⚠ **2つの期限を混同しないこと**（2026-09-05 に確認）。サーバーへ届く力＝`token` は **30日**で切れる
（`TOKEN_TTL_MS`）。切れた後は合言葉なしに新しい token は取れない（`enterRoom` が `authKey` を要求するため）。
一方 **`encKey` と平文の控えには期限が無い**＝**端末に残った内容を読むことは何年経ってもできる**。
⇒ 「30日で切れるから大丈夫」は成り立たない。切れるのは同期であって、漏れる中身のほうではない。

**これは実装の事故ではなく、意識して選ばれた取引である。** `session-store.ts` の冒頭コメントが
同じことを既に書いている（要旨:「復号鍵をこの端末に置くということ。合言葉を毎回打たずに済む代わりに、
この端末を使える人はこの部屋を開ける。共用端末では『この端末から消す』を使う。オフラインで開けるように
するにも、鍵が手元に無いと成立しない」）。⚠ **矛盾していたのは実装ではなくこの設計文書のほうだった。**

鍵を永続化しないと成立しないもの＝この節の表そのもの。`enterRoom()` は
`GET /api/rooms/:id/salt` と `POST /api/rooms/:id/enter` の**2回の通信**を要求するので、
保存された `token` / `encKey` が無ければ**圏外での開き直しは原理的に不可能**になる。
「鍵を永続化しない」と「オフラインで閲覧・追記できる」は、この設計では同時に持てない。

⇒ **現時点の方針はコメント側に合わせる＝鍵は端末に置く。** 緩和は今のところ1つしかない:

- **「この端末から消す」導線**（ホームの各部屋のボタン → `dropLocal()` + `forget()`）＝**事後の削除だけ**
- 🔴 **「覚えさせない」という選択肢は存在しない。** `remember()` は部屋の作成時（`app.ts` の作成成功時）と
  入室時（`doJoin`）の**両方で無条件に呼ばれ**、UI にも「この端末に覚えない」に当たるものが無い
  （2026-09-05 に確認）。⇒ 共用端末では、**開いた瞬間にもう鍵が置かれている**＝利用者に残されているのは
  「後で消す」だけで、「置かせない」ではない。**この差は説明文では埋められない**ので、
  取引を本当に選ばせるなら入室画面に選択肢を足す実装が要る（Phase 2 の判断材料）
- ⚠ 上記を説明する UI 文言とプライバシーポリシーへの反映は**まだ書かれていない**。§11 の記述もこの点に触れていない

⚠ **ローカルの状態だけを暗号化しても防御にはならない。** 鍵を同じ `localStorage` に置く限り、
中身を読める攻撃者は鍵も読める。「ローカルも暗号化する」を本当に成立させるには
**鍵を端末に置かない＝毎回合言葉を打たせる**設計へ戻すしかなく、それはオフライン耐性（§4.2 の軸の片方）と
引き換えになる。**Phase 2 の判断材料として残す。**

### id の採番

オフラインで連番を採番すると複数端末で必ず衝突するため、**booking の id はクライアントが UUID を生成する**。

### 9.1 圏外入室券（2026-09-06）

**電波の無い場所で、同行者を部屋に入れる。** 幹事の画面に QR を出し、相手は
**OS のカメラ**で読む。読んだ先は `/r/<部屋ID>#t=<券>` で、券には
salt・反復回数・kdfVersion・iv・暗号文が入る。相手は聞いた5語を打ち、
**サーバーに一度も触れずに**復号して部屋の中身を見る。

**なぜこの製品にだけ作れるか**（§7.5 の帰結）:
- サーバーが暗号文しか持たないので、**券をどの経路で渡しても増える危険が無い**
- 鍵は端末で合言葉から作るので、導出に通信が要らない
- 合言葉が違えば AES-GCM のタグ検査が**端末内で**弾く。サーバーに問い合わせない
- 殻は Service Worker がキャッシュ済みなので、圏外でもアプリ自体が開く

**決めたこと**:

| | |
|---|---|
| 読み取り | **OS のカメラ**（アプリ内にデコーダを持たない＝0バイト。WebKit に BarcodeDetector が無い問題も回避） |
| 大きい部屋 | QR の上限（約1,270バイト＝20〜25件）を超えたら **ファイル渡し**へ切り替える。⚠ AirDrop とクイックシェアは相互運用しないので、**同じ OS 同士でしか効かない**。QR が主・ファイルが副 |
| `authKey` | **端末に保存しない。** 保存すると §9 の「30日で再認証」という性質が消え、盗まれた端末でできることが広がる。最初の `/enter` が通るまで記憶の中だけに置く |
| カスタム合言葉の部屋 | **券を発行しない**（§7.6.1 ② の追記を参照） |
| 券の中身 | **スナップショット**。渡した後の変更は含まれない。電波が戻った時に §9 の3方向マージで合流する |

⚠ **正直に書くべき限界**（README へ）:
- 受け取る側は**一度 Michizure を開いたことがある**必要がある（殻のキャッシュ）。
  iOS は7日触らないとストレージを消すことがある
- 券は渡した時点の写し。相手がその後に足した記録は、電波が戻るまで見えない

### 衝突の扱い

オンライン復帰時、キューに積まれた操作をサーバーから取得・復号した状態と突き合わせる。

- **追加**: 衝突しない（UUID のため）。そのまま適用
- **精算チェック**: 冪等なのでそのまま適用
- **編集・削除**: 対象がサーバー側で変更されていた場合、スナップショット比較と同じ方式でユーザーに提示し、上書きか破棄を選ばせる

**完全な自動マージ（CRDT）は Phase 1 では実装しない。** 想定利用が「同じ旅行の同行者が数人」であり、同一の予約を同時にオフライン編集する確率が低いことに基づく。

## 10. インポート

現行アプリの「エクスポート」が出力する `{ state: { members, bookings }, nextId }` を受け取り、新しい部屋を作って流し込む。**変換も暗号化もすべてクライアント側で行う。** 平文がサーバーへ渡ることはない。

変換内容:
- `members`（文字列配列）→ `Member[]`（id を採番）
- `booking.id`（数値）→ UUID
- `payer` / `participants` / `paid` のキー（名前の文字列）→ Member の id
- `schemaVersion` を付与

**現行アプリには一切変更を加えない。** 既存のエクスポート機能をそのまま使う。

## 11. プライバシーとデータ削除

- **部屋の削除導線**: 合言葉から導出した `authKey` を提示できる人が削除でき、DO ごと破棄する
  - 🔴 **墓標（削除済みの印）を残さない＝削除済みと存在しないは区別できない**（2026-08-11 裁定・再litigate不要）。
    区別するには roomId と削除時刻を残す必要があり、**「削除＝完全に消える」というこの製品の中核の約束に例外を作る**。
    得られるのは UI 文言1つで、失うのは約束の一貫性と、法務照会・プライバシーポリシーの「保持するもの」が1項目増えること
- **自動削除**: 最終アクセスから1年。DO の Alarm API を使い、入室のたびに1年後へ再設定する。発火時に `lastAccessAt` を確認し、1年経過していればストレージを破棄する。外部の cron を持たずに済む
- **プライバシーポリシー**: 保存する内容を**正確に**書く。すなわち「暗号文」と「§7.5 に列挙したメタデータ」。**「何も保存しない」「運営者には見えない」と書いてはならない**
- **利用規約**: 個人開発・無保証であることを明記
- **合言葉紛失時の復旧不可**を利用規約と UI の両方に明記

## 12. エラー処理

| 状況 | 挙動 |
|---|---|
| 部屋が存在しない | 明示的なエラー画面。トップへ誘導 |
| 部屋が削除済み | **存在しない部屋と区別しない**（同じエラー画面）。2026-08-11 裁定 |
| 合言葉違い | 残り試行回数を示さずに拒否。連続失敗で指数バックオフ |
| 復号に失敗 | **区別していない。** `app.ts` の `doJoin` は `enterRoom` と `loadState` を同じ `try` に入れており、復号の失敗（WebCrypto の `OperationError`）は `invalid_key` / `too_many_attempts` / `not_found` のどれにも一致せず「入室に失敗しました: …」へ落ちる |
| WS 切断 | **1秒から倍々で最大30秒までの指数バックオフで再接続**。切断中はオフラインモードとして動作 |
| 編集中に他端末が変更 | クライアント側の衝突検出（スナップショット比較 + 確認ダイアログ） |
| メンバー上限超過 | クライアント側で拒否（§7.4 の限界を承知のうえ） |
| 暗号文のサイズ超過 | サーバーが 413 で拒否 |

⚠ **この表の2行は、実装と食い違ったまま長く放置されていた**（2026-09-05 の監査で発見）。直し方が2行で違う:

- **WS 切断 — 実装が意図的に分岐した。設計文書の側を実装に合わせた。**
  当初は「5秒間隔で再接続」と書いていたが、`src/client/live.ts` は指数バックオフを選び、
  コメントで固定間隔を名指しで否定している（要旨:「一定間隔で叩き続けない＝圏外のまま電池と通信量を使い切る」）。
  山中・海外・機内・地下という §4.2 の想定利用では**圏外が長く続きうる**（実際の継続時間は未計測）ので、
  固定間隔で叩き続けない実装の判断のほうが正しい。
  ⇒ **設計文書が誤っていた。** 直したのは実装ではなくこちら。
- **復号に失敗 — こちらは実装が設計に届いていない。** 「データ破損として区別して表示する」は
  書かれただけで実装されなかった。⚠ **利用者から見ると原因の見当がつかない**＝合言葉は正しいのに
  「入室に失敗しました」とだけ出るので、合言葉を打ち直し続けることになる（打ち直しても直らない）。
  しかも `authKey` は一致しているので**失敗回数に数えられず、バックオフという手掛かりすら出ない**
  （§7.2 の関門は `authKeyHash` の不一致でしか進まない）。
  ⚠ **直す時に `doJoin` だけ見ないこと。** 復号が走る経路は他に2つあり、どちらも別の顔で隠している:
  `openRemembered` の `pull()` は失敗を「つながりません。合言葉で入り直してください」＝**通信のせいにして表示**し、
  WebSocket で届いた更新の `decryptBlob` は**黙って捨てる**（「自分の鍵では読めないもの」として無視する。
  他人の暗号文を無視する目的では正しいが、自分の部屋が壊れた場合と区別できていない）。
  ⇒ **改善候補として残す。** 表は現状（区別していない）を書いてあるので、「区別している」と読んで
  設計判断を積み上げないこと。

## 13. テスト方針

`vitest-pool-workers` で DO のユニットテストを書く。以下は必須とする。

1. **鍵導出** — 同じ合言葉とソルトから同じ `authKey` / `encKey` が出ること、`authKey` から `encKey` が導出できないこと
2. **暗号化と復号の往復** — 平文が復元できること、IV が毎回異なること
3. **認証** — 正しい `authKey` の受理、誤りの拒否、連続失敗時のバックオフ
4. **サーバーが平文を受け取らないこと** — 送受信するペイロードに平文の文字列が現れないこと
5. **送信者除外が実際に効いていること**（§8 の理由により名指しで必須）
6. **部屋の分離** — 別の部屋のデータが混ざらないこと
7. **インポートの同一性** — 変換前後で金額・対象者・精算状態が一致すること
8. **精算ロジック** — `parts()` / `isDone()` / `settle()` の移植後の同値性
9. **オフラインキューの適用** — 追加・精算チェックが復帰時に正しく反映されること
